# Maintain a verification skill

A feature map rots the moment the app changes. This is the upkeep loop for a skill generated by the `create-verification-skill` skill, or any project-local verification skill with a feature map. The unit of rigor is the feature. Cover every feature file from source and exercise every feature live.

## Outcomes

Pick one and say which.

- **clean.** Every feature got source and live coverage. Nothing worth shipping. No branch, no PR.
- **changed.** One PR ships proven doc, harness, or map corrections.
- **blocked.** Coverage could not finish, or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only the verification skill's own directory: its SKILL.md, `features/`, and any helper scripts it owns. Never edit product code during a run. A behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, do not paper over it in docs).

## Pass

0. **Locate the target.** The project-local skill whose body has Launch and Drive sections and a feature map, usually `.claude/skills/verify-*/`. With several candidates, ask which with `AskUserQuestion`. With none, stop and point at the `create-verification-skill` skill instead of inventing a target.
1. **Index hygiene.** Read the feature map README and glob its sibling files. Fix missing, extra, duplicate, or dead entries. Lightweight, no generated inventory.
2. **Source wave.** One `Agent` per feature file, all in one message, `subagent_type: "bstack-agent"` on the bulk-reading model (`../bstack-mode/references/models.md`). Pass `references/source-reader.md` verbatim with the paths substituted. Readers never drive the app and never edit files.
3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift yourself; do not re-prove clean claims. Sweep recent churn (`git log` over the user-facing dirs) for surfaces missing from the map. Require a concrete source path before calling one missing.
4. **Live pass.** Required even when source looks clean. You own all driving. Follow the verification skill's own Launch model, one long-lived instance driven serially for daemons, services, and UIs, or a fresh isolated session per drive for short-lived CLIs. Its Launch section decides, not this one. Exercise every feature at least once and hold three invariants the whole pass, whatever fails:
   - Never drive an instance you have not health-checked since it last did something surprising. Doctor before the first drive, on each fresh session, and after any failed drive. Where doctor cannot see the failure (a wedged UI on a healthy process), reset to a known state or relaunch rather than hope.
   - Evidence captured so far survives every cleanup, checked at its named location, not assumed.
   - Nothing a drive started outlives that drive's usefulness. Clean failed-iteration residue whether the session is stuck, exited, or shared. For a shared instance, clean the residue, not the instance.

   A doctor failure caused by skill drift is drift. Fix it under edit scope and retry once, restarting only what the fix invalidated, before calling the pass blocked. A feature that cannot be reached is `verified-unreachable` only with the concrete prerequisite (auth, hardware, OS, external state) and the route attempted. If the map omits that prerequisite, that is drift. Any harness fix from triage gets re-driven live before it ships. Final teardown happens after the last drive of the run, re-proofs included. Evidence stays.
5. **Triage.** A wrong or missing user-POV description is doc drift. Fix it. Working behavior the harness cannot drive is a harness gap. Fix it, keeping scripts executable with the invocation shown in the skill body. App behavior that is actually broken is a product gap. Record it for the user and keep it out of this PR.
6. **Ship or stop.** For changed, re-read every changed file, then run **Opening a PR** (`../bstack-mode/playbooks/opening-a-pr.md`) for one PR of proven corrections. For clean or blocked, no PR.

Keep run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in the scratchpad. Do not commit them.

**Reply:** the outcome, features covered live and how each was proven, drift fixed, product gaps found, and the PR link when one shipped.
