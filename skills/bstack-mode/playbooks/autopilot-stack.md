### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the user one linear base-branch stack to review and land.** For a queue where the user wants to review before landing, the work is sequenced or coupled, or merge authority was not granted. Independent PRs with landing authority granted is `playbooks/autopilot-full.md`. A multi-day program whose coordinator lands work itself is `playbooks/orchestrate.md`. Pushing branches and opening PRs are outward-facing, and the explicit go in step 3 is the ask that covers them. Every forge operation is `gh`.

1. **Run the owner loop unchanged.** One `bstack-agent` per PR on the code-delegate model (`references/models.md`) in `isolation: "worktree"`, owning its change end to end: build, first push, a ready PR opened before self-proof, self-proof on the real artifact (`principles/prove-it-works.md`) with gates, CI, and receipts, review-comment triage on the merits (fix real findings, dismiss noise with a concrete reason), a read of its whole diff to cut comments that narrate what the code does, and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the `show-me-your-work` skill, pushes its first branch snapshot, and opens the PR ready, never draft. Keep the trail uncommitted and return it in the report.
2. **Audit on a wake chain.** Run an audit tick roughly every 30 minutes, armed with the `loop` skill, never left to memory or to completion notifications. At each tick, re-read `playbooks/autopilot-stack.md` and the program objective, audit the operation against both, and fix drift in that tick. Probe each owner read-only (`gh`, pushed branches, `bstack-trace` on its transcript). Count only side effects as progress: commits, pushes, PR or check deltas, trail rows. A lane past its expected runtime with no side effect is stuck. Stand it down and dispatch a replacement at once.
3. **Hold the user gates.** State-then-wait, so a request to state the plan is not a go. On the user's explicit go, write the full program objective at the top of the trail and re-read it every tick until the chain is done. On the user's stop, stop every running owner and log the hold. Nothing writes until the user releases it.
4. **Verify at STACK-READY.** The owner reports STACK-READY with the exact head SHA. Spawn independent verifiers at that SHA, one per lane, in one message, on a model other than the owner's. The lanes: re-run the gates, prove the load-bearing behavior live on the real surface (the `run` skill), and audit receipts and diff while distrusting the PR body. Aggregate to one verdict. Findings go back to the owner. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms `--auto`, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the user specified.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease` only after a `git ls-remote` check, and set the base with `gh pr create --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk.
7. **Absorb drift at the root, then re-verify what moved.** Fetch trunk and rebase the chain bottom to top. When a rebase conflicts in an owner's files, that owner fixes its slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Compare each PR's `git patch-id` at its verdict SHA against the new base-to-head diff. An unchanged patch-id keeps the code verdict. A changed patch goes back through step 4 before delivery. Re-run mergeability and CI after every rewritten push regardless. The countersign rule from `playbooks/autopilot-full.md` applies. A genuinely new pin raise stops for the root's fresh countersign, and absorbing landed values is not a raise.
8. **Deliver the chain.** One linear chain of verified PRs, reviewable bottom-up on GitHub, every link carrying its verifier verdict in the PR body or a comment. The user reviews and lands it, by hand or by arming merge-when-ready. If the user then asks you to land it, that is `playbooks/shipping.md`.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
